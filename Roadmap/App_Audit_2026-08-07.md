# App Audit — 2026-08-07

**Scope:** whole-app audit of `Priceback` (mobile + backend) for **path accuracy** and
**bugs**, with every finding ranked by criticality.
**Commit audited:** `66a14e4` (`main`, clean tree) · app version **2.8.4** / vc 24.
**Method:** read-only. No source file was modified. `npm run i18n:check` and
`npm run typecheck` were run (both are non-mutating); the Jest and backend suites were
**not** run locally — that is a standing rule, CI is the authority there.

**Nothing in this document has been fixed.** Each finding carries its evidence, its
file:line, and a proposed fix so the repairs can be scheduled independently. Two items
(**H1**, **L5**) are facts about the *hosting environment* that cannot be established
from the repository — they are marked **VERIFY** and must be confirmed against EAS /
Railway before being treated as confirmed defects or closed.

### 1b. Looked risky, verified sound

Four things that a reasonable auditor flags on sight and that turn out to be correct.
Recorded so they are not re-raised.

- **16 async Express routes have no `try`/`catch`** — but this is *already handled
  structurally*. `wrapAppRoutes(app)` (`backend/server.js:72`) patches the routing methods
  and runs **before** the first route registration (line 988), so a rejected handler
  becomes `next(err)` rather than a process-killing unhandled rejection. This is the fix
  from Bugs #138 and it is intact. Do not "fix" the 16 routes by hand — the whole point of
  that design was that the *next* route is covered too.
- **Ordinal-indexed receipt-item routes** (`/api/receipts/:id/items/:index/{claim,watch}`
  and `DELETE`) are safe despite looking like a shift hazard. `receiptsRepo` resolves the
  ordinal over the `deletedAt IS NULL`, `position`-ordered list — the same set the client
  indexes — and verifies a `{lineTotal, quantity}` fingerprint before acting, falling back
  to a fingerprint search when the ordinal misses.
- **`POST /api/unwatch` is dead but harmless.** `/api/watch` **replaces** the entire
  watch list for a key on every call, and the client posts the full active set from
  `HomeScreen` / `DetailScreen`, so unwatching is implicit by omission. (It is still dead
  code → **L4**.)
- **The admin Profile menu is properly gated.** `isAdmin` is server-authoritative and the
  endpoints re-enforce it, so the client-side hide is defence in depth, not the control.

## 2. 🔴 High

### H1 — OTA updates cannot reach production builds: no update `channel` — **VERIFY**

**Evidence.** `app.json` wires EAS Update completely: `updates.url`
(`https://u.expo.dev/d5dff4b7-…`), `updates.codeSigningCertificate`
(`./certs/certificate.pem`), `updates.codeSigningMetadata`, and
`runtimeVersion: { policy: "appVersion" }`. The certificate is committed and
*deliberately* re-allowed past the blanket `*.pem` rule in `.gitignore`. Everything about
the repo says "OTA hotfixes are a capability we have".

But `eas.json` declares `"channel"` on **one** profile:

```
eas.json:33      "dev": { "extends": "preview", "channel": "dev", … }
```

`production`, `preview` and `development` declare none. A build created without a channel
is not bound to an update branch, so `eas update --branch <x>` has nothing to match it
against and the update is never delivered.

**Why it matters.** This is the difference between "we can ship a JS hotfix in an hour"
and "we wait for a full store review". It fails *silently* — `eas update` reports success
and publishes the bundle; the bundle simply never reaches a device. It is exactly the kind
of thing discovered during the incident it was supposed to solve.

**Verify first** (this cannot be settled from the repo):
```
eas channel:list
eas build:view <latest-production-build-id>   # does it report a channel?
```

**Fix.** Add `"channel": "production"` to the `production` profile (and matching channels
to `preview` / `development` if internal OTA testing is wanted). One line each. No code
change, no rebuild of anything already shipped — but note the fix only takes effect for
**future** builds: binaries already in the store were built channel-less and stay that
way.

**Effort:** minutes. **Risk of the fix:** low, but it *activates* a delivery path that has
never carried traffic — the first production `eas update` after this should be a no-op
bundle, verified on a device, not a real hotfix.

### H2 — Five admin-token routes accept unlimited guesses, which bypasses the throttle on the routes that have one

**Evidence.** `_adminTokenOk` (`backend/server.js:3282`) does a length-guarded
`crypto.timingSafeEqual` — and **no rate limit**:

```js
function _adminTokenOk(req, res) {
  if (!ADMIN_TOKEN) { sendUnconfigured(res, "ADMIN_TOKEN/FLYER_ADMIN_TOKEN"); return false; }
  const token = req.get("x-admin-token") || "";
  const a = Buffer.from(token), b = Buffer.from(ADMIN_TOKEN);
  if (a.length !== b.length || !crypto.timingSafeEqual(a, b)) { /* 401 */ return false; }
  return true;
}
```

Unthrottled callers:

| Route | Line | What it can do |
|---|---|---|
| `POST /api/admin/users/:sub/flag` | `server.js:3303` | block a user's credits + subscription |
| `DELETE /api/admin/users/:sub/flag` | `server.js:3314` | unblock a flagged user |
| `POST /api/admin/price-points/:id/verify` | `server.js:3330` | mark an observation verified — **releases deferred credits** |
| `POST /api/check-all` | `server.js:5841` | kick the price-check + verified-drop sweeps |
| `POST /api/admin/price-tag-credits/revoke` | `server.js:3073` | revoke granted credits (inline compare, same gap) |

Meanwhile the two routes that *do* throttle call it **before** the compare, precisely so
failed guesses are counted:

```
server.js:3492   /api/flyer/import          → checkFlyerImportRateLimit(ip)
server.js:3664   /api/admin/barcode-links   → checkFlyerImportRateLimit(ip)
```

The codebase has already made this decision. These five routes simply never got it.

**The sharp edge.** `ADMIN_TOKEN` falls back to `FLYER_ADMIN_TOKEN`:

```
server.js:585    const ADMIN_TOKEN = process.env.ADMIN_TOKEN || FLYER_ADMIN_TOKEN || null;
```

Unless `ADMIN_TOKEN` is set separately in Railway, the two are **the same secret**. So an
attacker brute-forces it unthrottled against `/api/admin/users/:sub/flag`, then spends the
recovered token on the throttled routes. The throttle protecting `/api/flyer/import` is
therefore not just missing elsewhere — it is *defeated*. That is a strictly stronger
version of Bugs #139, which was about bypassing this same throttle by rotating a header.

**Blast radius:** money and access — credit revocation, credit release, and the ability to
block or unblock any account.

**Fix.** Move the throttle inside the shared helper so it cannot be forgotten again:

```js
function _adminTokenOk(req, res) {
  if (!ADMIN_TOKEN) { … }
  const rl = checkFlyerImportRateLimit(clientIpForRateKey(req));   // BEFORE the compare
  if (!rl.allowed) { res.set("Retry-After", …); /* 429 */ return false; }
  …
}
```

One place, covers all five. Then convert `/api/admin/price-tag-credits/revoke` (3073) from
its inline compare to `_adminTokenOk` so there is exactly one admin-token path. Note
`app.set("trust proxy", 1)` (`server.js:42`) is already in place, so `req.ip` is not
forgeable — the #139 fix holds.

**Effort:** ~30 min including tests. **Risk:** low; the limiter and its per-IP bucket
already exist and are exercised by two routes. Add a test that a 429 is returned *before*
a correct token would have been accepted, so the ordering can't silently regress.

## 3. 🟠 Medium

### M2 — French users see an English sentence on the price-tag deal badge

**Evidence.** `src/screens/PriceTagScanScreen.js:924`:

```jsx
<Text style={[db.detail, { color: style.ink }]}>{detail}</Text>
```

`detail` comes straight off the backend's `DealSignal`
(`backend/services/priceSignalService.js`) and is English prose, e.g.:

> "Price ends in .97 — Costco corporate officially marked this down. Limited time. BUY NOW."

There is **no** `priceTag.deal.*Detail` key in `src/services/i18n.js` for any of the five
signal codes. On the *same badge*, `tier`, `label`, `asterisk_note` and `organic_note` are
all correctly routed through `t()` — so this is an oversight, not a decision.

**Why it matters.** Direct violation of the CLAUDE.md standing rule 5: *"Labels that
arrive from the backend … are English data, not display text."* Price-tag scanning is a
headline feature and the deal badge is its payoff moment. `CreditHistoryScreen.js:131`
shows the correct pattern being applied elsewhere (`ledgerNote()` maps server notes to
translated labels, with a comment saying exactly why), which makes the gap harder to
defend.

**Fix.** Add `priceTag.deal.detailRegular` / `detailMarkdown97` / `detailManufacturerPromo`
/ `detailManagerMarkdown00` / `detailClearance88` in **both** EN and FR, and render through
the `hasKey()` overlay from **M3**. The enum is closed and only five entries wide.

**Effort:** ~45 min including FR copy. **Risk:** none — additive keys.

### M3 — `t(key) || fallback` is dead code: the intended server-string fallback can never fire

**Evidence.** `t()` resolves *active language → English → **the key itself***
(`src/services/i18n.js`, documented in its own header). The key is a non-empty string, so
it is always truthy. Therefore in `PriceTagScanScreen.js`:

```js
914:  const tierLabel = t(`priceTag.deal.tier${tier.charAt(0).toUpperCase() + tier.slice(1)}`) || label;
922:  … {t(`priceTag.deal.${signal.signal}`) || label}
```

…the `|| label` arm is **unreachable**. Both keys are built dynamically, so
`npm run i18n:check` cannot see them either (it validates literal `t("…")` keys only).

**Current state: latent, not live.** The producer enum is closed and fully mapped —
signals `{regular, markdown_97, manufacturer_promo, manager_markdown_00, clearance_88}`
and tiers `{normal, good, best}` all have EN + FR keys. So nothing is broken today.

**Why it matters.** The failure mode is delayed and lands on the wrong person. Add a sixth
signal code backend-side and the badge renders the literal string
`priceTag.deal.<new_code>` — worse than the raw code, and the author's intended fallback to
the server's English `label` never runs. Two standing rules bite here: *"never render a raw
code or identifier"*, and the explicit *"no `t(x) || "fallback"` crutch"*.

**Fix.** The right primitive already exists and is already used for exactly this —
`hasKey()` in `i18n.js`, per the `src/services/catalogLabels.js` pattern:

```js
const k = `priceTag.deal.${signal.signal}`;
const text = hasKey(k) ? t(k) : label;   // falls back to the server's English string
```

Apply to both sites, and to the M2 detail lookup. **Effort:** ~15 min. **Risk:** none —
behaviour is identical for all currently-reachable values, which is also what makes it
safe to land alongside M2.

### M1 — `preview` and `development` EAS builds self-report as production

**Evidence.** `eas.json` sets `APP_ENV` on the `dev` profile only. Both consumers default
the missing value to `"production"`:

```
config/profiles/eas.js:17     const APP_ENV = process.env.APP_ENV || "production";
app.config.js                 const appEnv = process.env.APP_ENV || "production";
```

So a `preview` or `development` build resolves `extra.appEnv === "production"`. Two
consequences:

**1. Sentry mislabels internal-test traffic as production.**
```
src/services/analyticsService.js:121    environment: Constants.expoConfig?.extra?.appEnv || "production",
```
Preview builds point at the **development** Railway backend
(`PRICE_API_URL=https://priceback-development.up.railway.app`) yet file their crashes and
errors under `production`. Production error rate, crash-free sessions and release-health
are all polluted by test traffic — at launch, which is precisely when those numbers have
to be trustworthy. `config/profiles/local.js` states the intent plainly ("Tags Sentry
events + analytics with the environment so local-build crashes are easy to filter out of
production graphs"); the EAS path doesn't honour it.

**2. A latent build blocker, and a comment that misdescribes the code.**
`assertStoreBuildIsPurchasable` in `app.config.js` documents itself as: *"Fires only for
`--profile production` … Local builds, dev/preview profiles, and `expo start` are
untouched."* Because it gates on `APP_ENV || "production"`, it in fact **also runs for
`preview` and `development`** and will `throw` — failing the build — unless
`REVENUECAT_API_KEY_{IOS,ANDROID}` is present in that EAS environment. Whichever way this
is resolved, code and comment currently disagree.

**Fix.** Add `"APP_ENV": "preview"` and `"APP_ENV": "development"` to the respective
profiles in `eas.json`. Then re-read the preflight comment and make it true — either it
genuinely covers production only (it will, after this change) or the comment should say it
covers every EAS build.

**Effort:** ~10 min. **Risk:** low, but it *changes the Sentry environment tag* for
preview builds — existing Sentry alerts, dashboards or release-health rules filtered on
`environment:production` will stop seeing preview traffic. That is the intent; it should
still be announced rather than discovered.

### M4 — Hardcoded English UI strings in two user-facing screens

**Evidence.**

| File:line | String | Screen |
|---|---|---|
| `src/screens/ScanScreen.js:1481` | `<Text …>QTY</Text>` | receipt review — a core path, on every scan |
| `src/screens/DetailScreen.js:1240` | `placeholder="Item name"` | item editor — sits directly beside a correctly-translated `t("detail.editName")` |

**Why it matters.** Violates CLAUDE.md rule 1 (*"A literal in JSX is a bug"*). Note that

`StoresAndProfileScreens.js:1716`) are **format masks**, not prose, and are identical in
both languages.

**Effort:** ~15 min. **Risk:** none.

### L2 — `PaywallScreen` and route `"Paywall"` are registered but unreachable

Registered at `App.js:470`; nothing navigates to it. The file (33 lines) is unchanged
since the commit that introduced it (`b957f43`). All three real entry points instead use
`navigate("Scan", { showPaywall: true, paywallOnly: true })` —
`HomeScreen.js:477`, `ManageSubscriptionScreen.js:506`, and internally in `ScanScreen`.

### L4 — `POST /api/unwatch` is dead code

`backend/server.js:2170`. No callers; unwatch is implicit because `/api/watch` replaces

### L5 — `DATA_DIR` is not set in `railway.json`, so file-backed state may be on ephemeral disk — **VERIFY**

`backend/railway.json` sets no `DATA_DIR`, so `backend/server.js:271` falls back to
`path.join(__dirname, "data")` — inside the container image. The code already warns about
this in two places:

```
server.js:266    // On Railway, the container filesystem is ephemeral — every redeploy wipes
                 // it. Set DATA_DIR to a mounted Railway Volume (e.g. /data) …
server.js:1330   // so a Railway redeploy mid-window does NOT reset them — keep DATA_DIR on a
                 // [mounted volume]
```

Files at stake: `watched.json` (the whole price-watch registry), `watchedTouched.json`,
`notifyLedger.json` (the send-once dedupe ledger), `flyerOffers.json` / `flyerHistory.json`
(the active flyer overlay — the *primary* price source), `ocrBudget.json`, and the daily
analytics logs.

**This is an ops fact, not a code defect** — `DATA_DIR` may well be set as a Railway
service variable with a Volume mounted. **Verify** in the Railway dashboard for both the
production and development services. If it is *not* set: a redeploy silently drops the
watch registry (price-drop pushes stop until each user next opens the app), resets the
notify dedupe ledger (re-notifying drops already sent), and wipes the flyer overlay.
Mitigating factor: `flyerOffers` and the OCR budget have documented DB/`kv_state`
counterparts, and the client re-registers watches on Home/Detail focus — so the failure is
degradation, not permanent loss.

### L6 — *(Priceback-Website)* the `_headers` rule `/*.html` can never match

`_redirects` 301s every `.html` URL to its extensionless form
(`/privacy-policy.html → /privacy-policy`, and so on for all nine pages), so no request is
ever *served* at a `.html` path. The `/*.html` block in `_headers` — intended to give HTML
`Cache-Control: public, max-age=0, must-revalidate` so content and SEO edits go live
immediately — therefore never applies, and HTML falls back to Cloudflare's defaults.

**Fix:** change the pattern to `/*`, or enumerate the clean paths. Cross-repo
(`Priceback-Website`), so it does not belong in the app's fix batch.

### L7 — `placeholder="YYYY-MM-DD"` is not localized

`src/screens/ScanScreen.js:1721`. French convention is `AAAA-MM-JJ`. Genuinely trivial, but
it is display text and the rule has no exceptions. Roll into the M4 fix.

## 5. Deliberate choices — not findings

Found during the audit and confirmed intentional. Recorded so a later pass does not
re-raise them.

- **Route `BrandChart` is unreachable on purpose.** The Profile menu row is commented out
  at `src/screens/StoresAndProfileScreens.js:712` with the note *"Brand chart row hidden
  for Profile B — route/screen/i18n kept registered; uncomment to restore."*
- **`cors({ origin: "*" })`** (`backend/server.js:55`) is intentional and documented: the
  only client is a native app using Bearer tokens, with no cookies and no browser
  same-origin context. Tightening is tracked in `Security/SecurityRecommendations.md`.
- **`watchedRepo` is dormant** by design — the `watched_items` table is intentionally not
  created, and the header documents the exact steps to re-enable so the change is a pure
  revert.
- **`/api/admin/barcode-links` (plural) and `/api/admin/barcode-link` (singular)** are two
  deliberately distinct routes: token-auth for the off-Railway harvester, and admin-user
  auth for the in-app feeder. Not a typo.
