# App Audit — 2026-11-09 (main @ v3.6.1, eve of the Kickstarter launch)

**Scope:** whole-app audit of `Priceback` (mobile + backend) on `main` for **bugs, gaps and
production risks with a real impact on shoppers**, every finding ranked by severity.
**Commit audited:** `70991cb` (`main` = `origin/main`, clean tree, tag `v3.6.1`) · app **3.6.1** /
build **60**. Prod minimum build is **56** on both platforms, so the live estate is **v3.3.0 → v3.6.1**
(builds 56–60); every backend finding below is judged against that whole range.
**Method:** read-only on the code. Both suites were run **locally** (mobile: all green; backend: the
files CI last reported red, re-run alone), `npm run i18n:check` and `npm run typecheck` were run, and
**production was read, never written** (Supabase prod via SQL `SELECT`s, Railway logs/variable *names*,
the public `/health`). No source file was modified. GitHub Actions was **not** dispatched (standing rule).

**Nothing in this document has been fixed.** Each finding carries its evidence, the builds it touches,
and a proposed fix, so the repairs can be scheduled independently next week. The previous whole-app
audit is `App_Audit_2026-08-07.md` (v2.8.4); its §1 checks were re-run here, not assumed.

### 1b. Looked risky, verified sound

- **`OCR_HOURLY_LIMIT = 30` / `OCR_DAILY_LIMIT = 200`** are **per device**, with a 5× **per-IP** brake
  (`checkOcrRateLimit`, `server.js` ~1845–1881) — a warehouse NAT full of launch-day scanners does not trip
  them. The *monthly* Vision budget is the global one → **H2**.
- **The locked-drop push says "only a few days left" whatever the real deadline.** That is deliberate
  (`pushI18n.js:159` — never reveal the deadline to a locked shopper); the failing test in **M1** is stale,
  the copy is not wrong.
- **Sign-in blocks on a failed hydrate** (`HYDRATE_TIMEOUT_MS = 12 000`, PR #147). By design; a cold-start
  hydrate (`reason: "boot"`) is `catch(() => {})` and never blocks an already-signed-in shopper.
- **Prod pool.** `DB_POOL_MAX` unset on Railway → default **5**; Supavisor session pooler cap is 15; 14
  connections were open at audit time but 10 of them are Supabase's own (Supavisor idle ×5, pg_cron,
  PostgREST, exporter, two of Maxim's VS Code tabs). The app pool is not near the ceiling.
- **Dropped receipts for locked stores on old builds.** `POST /api/receipts` → `422 STORE_NOT_AVAILABLE`
  (3.6.1 server) is terminal for builds 56–59: the receipt stays on the phone, shown "not backed up" on
  3.5.1+, silently on 3.3.0–3.5.0. Acceptable — those receipts are refused on purpose — and no charge.

## 2. Findings

### 🔴 High

#### H1. A refund the shopper never got is shown as **Claimed** and added to "total saved"

**Evidence.** Two rules, written three weeks apart, contradict each other:
- `AUTO_CLAIM_EXPIRED_DROPS = true` on prod (`backend/config/defaults.js:145`; sweep at
  `server.js:13588` → `receiptsRepo.autoClaimExpiredDrops()`): *"a charged drop whose claim window closed
  unclaimed is flagged claimed (`claim_source = 'expired'`) so the app counts it as saved"* (Maxim, 2026-10-17).
- The products view (#560, 2026-11-09): *"Claimed is final … missed savings belong under **Missed or
  expired** … show the year's missed savings next to the claimed total — never added into it"*
  (`src/services/productStatus.js:5–14, 41–43`).

The phone syncs `claimed: it.claimedAt != null` (`syncService.js:135`) and never reads `claimSource`
(only `AdminReceiptDetailScreen` does). So once the sweep runs, a missed drop moves from **Missed or
expired** to **Claimed**, leaves `missedSavingsInYear` (`productStatus.js:54` skips `it.claimed`) and is
summed into Home's "total saved" (`HomeScreen.js:354–355`).

**Prod today:** of 76 claimed lines, **58 are auto-claimed expired** (`claimed_savings` **$231.44**,
24 shoppers) vs **13** claimed by a shopper (**$50.50**, 9 shoppers) and 5 with no source. **≈82 % of the
"saved" money the app shows was never refunded.**

**Builds:** all (the flag is server data).
**Proposed fix (Maxim decides which rule wins):**
1. *Server, additive:* emit `claimSource` on every bootstrap/receipts item (it is already in the admin view).
   Decide the flag: keep it (so the receipt files under *claimed* for the policy-status heal) **or** set it
   `false`; if kept, the heal should set `policy_status` without setting `claimed_at`.
2. *Phone (3.6.2):* `productChip` → `"expired"` when `claimSource === "expired"`; `missedSavingsInYear` and
   Home's claimed sums skip such lines. Old builds keep showing them as claimed until they update — which is
   what they do today, so nothing gets worse.
3. *Datafix (optional, after 1):* `UPDATE receipt_items SET claimed_at = NULL WHERE claim_source_id = <expired>`
   if Maxim wants the 58 lines back under *Missed* for every build at once.
**Roadmap:** P1 (server) + P2 (3.6.2).

#### H2. Vision OCR has 805 scans left for the month, and the cap is a hard 503 for everyone

**Evidence.** prod `kv_state.ocr_budget.vision = { key: "2026-11", used: 195 }` on Nov 10 with
`OCR_MONTHLY_LIMIT = 1000` (the free-tier line, *"never billed"*). Past it, `POST /api/ocr` answers
`503 QUOTA_EXCEEDED` for **every receipt and tag scan until Dec 1** (`server.js:2670–2677`); the phone shows
"Scanning is temporarily unavailable" and drops into manual entry. The Kickstarter launch (Nov 10) brings new
shoppers whose first act is a scan; 73 receipts were filed in the last 7 days *before* any campaign traffic.
**Builds:** all.
**Proposed fix:** *today, as data:* raise `OCR_MONTHLY_LIMIT` in Admin · Quotas (Vision is ~US$1.50 per 1 000
past the free tier; a 5 000 ceiling caps the month at ~US$6) and confirm GCP billing is enabled on the Vision
project (else Google itself returns 429/403 → our 502). `ALERT_THRESHOLD_PCT = 80` already emails at 80 %.
*Roadmap:* make the monthly cap degrade (admin alert + per-device tightening) rather than refuse every shopper.
**Roadmap:** ops today; P1 for the soft cap.

#### H3. 42 verified drops wait for manual approval; two claim windows close **today**

**Evidence.** `PRICE_DROP_REVIEW_REQUIRED = true`, `SAVING_DROP_REVIEW_REQUIRED = true`,
`SAVING_DROP_AUTO_APPROVE = false`. `price_drop_review_queue`: **42 pending**, oldest queued **2026-10-25**
(16 days); rows **6032** and **716** sit on receipts bought 2026-10-11 whose 30-day window ends **2026-11-10**;
4837/8825 end 11-11; 3831 ends 11-12. A shopper is told nothing — and the commission is not charged — until a
human approves; a drop approved after its window is a missed refund that PriceBack saw in time. (`adminAlerts`
does push `price_drop_review` to admins; the gap is turnaround, not detection.)
**Builds:** all.
**Proposed fix:** *today:* approve the queue (desk). *Roadmap:* (a) an admin alert that names pending rows whose
window closes in ≤ 3 days; (b) auto-approve drops from **official** savings sources (Same-Day / costco.ca) that
pass every check, keeping review for third-party and receipt-pool drops — the "to confirm" tier already exists
in Solution B; (c) show the shopper a *"a drop is being verified"* state so the wait is visible.
**Roadmap:** ops today; P1 (a, b); P2 (c).

#### H4. The Kickstarter reward path (partner plan codes) has never run on prod

**Evidence.** Roadmap P0-2 asks to *"redeem one plan code on a real prod account end to end"* before Nov 10.
Prod: `partners` = 1, `partner_codes` = 1 with `referee_plan_months = 0`, **`partner_attributions` = 0 rows**,
`plan_granted_at` never set. No reward code with plan months exists, so the code → `_partnersRepo.redeem` →
`_grantOwedPartnerPlan` → RevenueCat promotional `unlimited` → app shows Unlimited chain
(`server.js:13433–13460`, `lib/partnerPlanGrant.js`) has only ever run in tests.
**Builds:** redemption UI is in Onboarding on every build; `refereePlanMonths`/`planGranted` are additive
(3.5.1+ name the plan).
**Proposed fix:** generate one plan code (`scripts/generate-partner-codes.js --per-pack`), redeem it on a real
prod account, confirm `partner_attributions.plan_granted_at` and the Unlimited entitlement in RevenueCat and in
the app; only then generate the backer codes.
**Roadmap:** ops, before any reward code is distributed.

### 🟠 Medium

#### M1. `main` is red on CI, and one backend test fails locally too

**Evidence.** The last two `workflow_dispatch` runs on `main` (11-05, 11-07) failed in the backend job.
Re-running the red files alone against the dev DB from this machine:
- `tests/priceDropLockedPush.test.js` — **2 stale assertions**: #556 changed the locked push to
  `🔒 Une baisse de prix a été trouvée` / *"only a few days left"*; the test still expects the old title and the
  real day count. Test defect, not a copy defect (see §1b).
- `tests/adminConsoleRoutesDb.test.js:278` *"a group that grew since the scan is refused rather than
  deleted"* — **fails locally as well** (`refused` has no `marker_users` entry). Either the test's group key
  is stale, or the purge's growth guard (`dataCleanupRunner.js:481–492`) does not fire when
  `remembered.counts[key]` is absent (`Number.isFinite(undefined)` → false → **no growth check → delete**).
  The second reading is a data-loss guard gap on an admin tool and must be settled by reading the scan payload.
- `tests/adminPriceLookupDb.test.js` — 111 ✖ on CI 11-07, **69/70 pass locally** today → CI-environment
  (shared dev DB residue), not code.
**Impact:** no green signal on `main`; the next real regression hides behind known reds.
**Proposed fix:** update the two push assertions; investigate the growth guard and fix whichever side is wrong;
re-dispatch on `main` once (Maxim's call).
**Roadmap:** P1 (this week).

#### M2. Builds 56–59 keep turning Outlook marketing emails into $0 "Costco" receipts

**Evidence.** Bugs #368: the mailbox import created 7 "Costco" receipts at $0 from shipping/marketing emails
(subject-as-item fallback) and 5 locked-store receipts. The locked-store half is closed server-side
(`422 STORE_NOT_AVAILABLE`), but the **$0 / no-priced-line half is phone-only** (`emailImportRefusal`, 3.6.1).
Costco is an open store, so `POST /api/receipts` still accepts a one-line `$0` receipt with no image from a
3.3.0–3.6.0 phone with an Outlook inbox connected. It then sits in the shopper's list, expired, unexplained.
**Proposed fix (server, additive refusal):** refuse a **new** receipt that has no priced line *and* no image
object (`422`, terminal, before the charge) — the same shape as the locked-store refusal, and one no camera
scan can produce. Old builds treat it as "not backed up" (3.5.1+) or stay silent (≤3.5.0); both are better than
a phantom receipt. State it in the PR's *Old app builds* section.
**Roadmap:** P1.

#### M3. Nothing tells the shopper a drop is pending review

Companion to H3, phone-side: between detection and approval the line shows *Watching*; after a rejection it
shows nothing. A *"Being verified"* state (released-drops list already carries queue state server-side) would
explain the wait and cut "the app missed my drop" tickets. **Roadmap:** P2 (3.6.2), after H3's server rows.
