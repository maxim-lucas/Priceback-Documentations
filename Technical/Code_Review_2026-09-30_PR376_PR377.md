## Findings and what was done

| # | Area | Finding | Fix |
|---|------|---------|-----|
| 1 | Queue billing | Two queue rows for ONE line (e.g. $40 staged by one sweep, $35 by the next, both approved) drained in one batch: both inserted in `price_drop_notifications` (different prices), both "won", both billed against the same pre-batch prior → the overlap charged twice, two pushes. Broke *commission charged exactly once*. | The drain keeps ONE row per line — the deepest — and closes the others as superseded. `priceDropRepo.recordNotified` enforces the same rule itself (defence in depth): one drop per line per call, lowest price wins. |
| 2 | Queue billing | A higher-price row approved AFTER a lower one was sent inserted cleanly (the unique index only stops the exact same price) → a stale "dropped to $40" push after "$35". | `recordNotified` (charge path) skips a drop at or above the lowest price already notified for the line — read inside the per-line advisory lock. The drain's re-check (row 3) also closes it. |
| 3 | Queue | Only `unitPaid > newPrice` was re-checked at drain time; a row can wait days for approval, and the verified price, the `excluded` flag, the materiality floor, the Executive gate, the source-tier authority could all have changed. | `_revalidate`: the drain asks `findNotifiable` again, scoped to exactly the claimed lines (new `receiptItemIds` option). A row holds only if the line is still a drop at its price or deeper AND the row's own saving clears today's floor. **The purchase window is judged exactly as the sweep judges it** — see "Not changed" below. |
| 4 | Queue billing | A shopper could claim a drop in-app while it was held for review; the claim made the line `live = false` and the drain superseded the row — **never charged**. Pre-queue it was billed seconds after detection. | A line claimed AFTER its row was staged (`claimed_at >= q.created_at` → `claimedWhileQueued`) is still billed when an admin approves it, with **no drop alert** (they already acted) and the usual charge notice. Rejected / never-approved drops still cost nothing. ⚠️ Behaviour change — see below. |
| 5 | Signup | `PUT /api/me/profile` treated ANY Terms grant as "completes signup". Every returning sign-in re-affirms the Terms through the durable profile-sync queue with no postal code → accounts without a valid code on file got 400 forever, wedging the whole merged payload: notification toggles and **marketing-consent withdrawals (CASL)** never reached the server. | "Completes signup" = the FIRST Terms grant (`consentRepo.hasGranted`). A re-affirmation from an account that already granted the Terms passes; a first grant without a code is still refused. The ledger is read only when it can change the answer. |
| 6 | Guarantee | `markDropsFound` was stamped from the raw candidates at detection — including drops an admin later rejects — ending the customer's Price-Drop Guarantee year for a drop PriceBack ruled not real. | Stamped only for CONFIRMED drops: at detection when review is OFF (minus any (line, price) an admin rejected, `priceDropQueueRepo.rejectedKeys`); on the drain when review is ON, dated to when the drop was staged (so a year is judged on its own drops however long review takes). |
| 7 | Queue | `stage()` was ON CONFLICT DO NOTHING in every status, so a row superseded because the line was briefly unwatched/edited blocked that (line, price) forever. | A superseded row is revived as pending (unreviewed, fresh queue time) when the sweep finds the drop again. Rejected and sent rows are still never re-staged. |
| 8 | Tag credits | Rule 8 (`applyTagExpiry`) stamps one shopper's EXP on EVERY price point for the product, so a dateless tag the route told "no credit" was paid once anyone scanned a dated tag. | Tag rows now carry `flags.printedExpiry` (did THIS tag print a date?); both settlement queries require it. Rows from before the flag (no key) keep the old rule and age out of the verification window. |
| 9 | Tag credits | Settlement read expiry on the UTC day; the route on the shopper's province day. From 20:00 in Toronto a tag on its last valid day was told "pending" and could never settle (the Bugs #292 class) — and since #377 every creditable tag has a date. | `settleVerifiedTagCredits` compares `valid_until` to the shopper's province day (`trackingTodayISO`); `settleAllVerified` enumerates loosely (UTC day − 1) and lets the per-pool settlement decide. |
| 10 | Tag parser | On a SAVINGS tag whose OCR also caught the fee-inclusive subtotal ("229.04 / + .95 / 229.99 / -55.00 / TOTAL 174.99"), the eco-fee pair (229.99) became the final price and the savings were added on top again → $229.99 / $284.99. | The pair is the price BEFORE the savings: final = pair − savings (confirmed by the tag when OCR caught it). The reverse arrangement (pair already net, pre-discount printed separately) is recognised. The six real prod fixtures are unchanged. |
| 11 | Queue | Queue `finalize`/`release` writes ran between the committed charge and the Expo send; if one threw, the batch was released and the error rethrown → **charged, never pushed**. | Post-charge bookkeeping is non-fatal (logged); the push always goes. A row it could not close is recovered after 15 min and loses the ledger election — never billed twice. |
| 12 | Pause | `setOpsFlag` only patched this process's snapshot: a `warm()` in flight could revert it, and other instances saw it up to 5 min late. | (a) warm() re-applies admin writes that landed during the refresh. (b) The drain reads the pause from `app_config` directly before EVERY pass (`configService.readOpsFlagFresh`). |
| 13 | Pause / drain | Pause checked once per drain (passes 2–3 ignored it); a re-run request during the last pass was dropped; a shopper's "Refresh prices" drained the WHOLE queue inside their request. | Pause re-read per pass; a request during the last pass schedules a follow-up drain; a user-scoped sweep drains only that shopper's rows (`claimBatch({ userSub })`), under its own key. |
| 14 | Queue | Undeliverable rows (muted, bad token, exemption blip) were released with a fixed 60-min back-off forever, showing "Approved — sending". | Back-off doubles per attempt (1 h, 2 h, 4 h … capped at 24 h), and the re-check closes a row once the drop stops holding. The admin screen says "not delivered yet (tried N times); retrying automatically". The drop stays owed — the pre-queue contract. |
| 15 | Admin OS | The account detail took the newest device that HAD an os; the list the newest device → the two screens could disagree. | Both read ONE query (`usersRepo._osSignalSql` / `accountOsFor`). |

## ⚠️ Behaviour changes to know about

1. **Claimed-while-held drops are billed on approval (finding 4).** #376's own test pinned "claimed after
   approval → superseded, never charged"; that test now pins the opposite. Rationale: the app shows a
   verified drop as soon as it is verified, independently of the queue, so with review ON most drops could
   be claimed before approval and escape the commission entirely. Before the queue they were billed seconds
   after detection. Only APPROVED drops are billed; a rejected or still-pending drop costs nothing, and the
   shopper gets the charge notice (not a "go claim it" alert). **Maxim's call if this should go the other way.**
2. **A revived superseded row returns to PENDING** (needs approval again when review is on), even if it was
   approved before it was superseded.
3. **The guarantee stamp waits for approval when review is ON.** A drop that sits unreviewed past the end of
   a guarantee year does not end that year.

## Not changed (deliberately)

- **The purchase window at drain time.** The review suggested superseding a drop approved after the store's
  adjustment window closed. `findNotifiable` itself does not gate on "today is inside the window" — since the
  2026-06-26 rework it notifies a drop whose price became available inside the window even if the sweep runs
  later ("detect in the past", Bugs #57). The drain re-check applies exactly that rule, so drain and detection
  stay identical. Tightening it is a product decision for both, not a queue fix.
- Commission arithmetic (telescoping totals), the per-line advisory lock, the single charge site.
