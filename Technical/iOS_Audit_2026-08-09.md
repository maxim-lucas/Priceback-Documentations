# iOS audit — parity with Android, and first-pass App Review readiness

**Date:** 2026-08-09
**Scope:** the whole iOS surface of the PriceBack mobile app, audited against
two references: the Android build (which ships and works), and Apple's recurring
rejection reasons.
**Branch:** `fix/ios-parity-and-review-readiness` (all six findings fixed)
**Status:** fixed in code and unit-tested; **not yet verified on hardware.**
**Bugs_Common_Fixes:** #157-#158 (this audit); #155-#156 are the Apple sign-in
crash and the Outlook search bug that preceded it.

---

## Why this audit happened

PriceBack has shipped on Google Play since 2.x. It has never passed — never even
reached — an App Store review. The single iPhone build that got as far as
TestFlight (2.8.1) died the moment Sign in with Apple was tapped; that crash was
fixed separately in PR #247 (Bugs #155-#156).

The concern that prompted this audit was that the crash was a *symptom*. iOS has
had a fraction of Android's real-device exposure, so any number of behaviours
could be silently wrong there while Android looks fine — and Apple rejects on
first submission for a category of things Play never inspects at all.

That turned out to be right. Six findings, all confirmed against primary
evidence rather than inferred: library type definitions, Expo's own prebuild
plugins, the installed React Navigation source, and the module import graph.
**Two are outright broken user flows on iPhone.** One of those is the single
control App Review is documented to exercise for auto-renewable subscriptions.

### F1 — "Restore Purchases" failed on a *successful* restore

`src/components/Paywall.js` called `catalogText(...)` to resolve the restored
tier's display name. It never imported it. Every other consumer does —
`ManageSubscriptionScreen.js`, `StoresAndProfileScreens.js`.

The call sits inside `handleRestore`'s `try`, which inverts the usual failure
mode:

- restore **succeeds** → `ReferenceError` → the `catch` shows the user
  "Restore failed", and `onPurchased` never fires, so an entitlement RevenueCat
  had just handed back is dropped;
- restore **fails** → the `else` branch runs → behaves perfectly.

`Paywall.js` is the app's **only** restore surface. App Review tests that control
directly with a sandbox subscription (Guideline 3.1.1). A reviewer would have
tapped it and been told the restore failed.

**Why it survived.** The existing coverage (`billingScreens.smoke.test.js`) mocks
`restorePurchases` to resolve `{ success: false }`. It only ever exercised the
branch that worked. A success-path test is now `__tests__/paywallRestore.test.js`.

> **The general rule.** When a handler's happy path and error path are both
> inside one `try`, a bug in the happy path *presents as the error path*. The
> "failure" message a user reports is then actively misleading — it names the
> branch that did not run. Mock success at least as carefully as failure.

### F3 — iOS forces a square crop, destroying the receipt

From `expo-image-picker`'s own type definitions:

> `aspect` — "This is only applicable on Android, since on iOS the crop
> rectangle is always a square."

Both content-ingest paths passed `allowsEditing: true`:

- `src/screens/ScanScreen.js` — a receipt picked from the photo library
- `src/screens/PriceTagScanScreen.js` — a price tag captured with the camera

A receipt is a tall portrait strip. On iPhone the user was forced through a
square crop that guillotined it before OCR ever saw it, so the parse failed or
returned a wrong total — and there was **no way at all** to submit a full receipt
from the library on iOS. Android's editor is free-form and works.

The code comment above the call asserted the opposite ("iOS … keep the system
picker with its manual editor"), treating the two system editors as equivalent.

**Fix:** `allowsEditing: Platform.OS !== "ios"`. iOS now passes the whole image
through, which is the same input shape the camera path (`takePictureAsync` →
`processImage`) has always shipped uncropped on both platforms — so it is a
known-good path, not a new one. Android is byte-identical.

If a confirm-the-crop step is wanted on iOS later, `expo-image-manipulator` is
already a dependency; that is a new UI surface with its own i18n and tests, and
was deliberately left out of a fix pass.

> **The general rule.** A cross-platform API that takes a boolean can still mean
> two different things per platform. `allowsEditing` reads as "let the user
> crop"; it actually means "free-form crop" on Android and "square crop" on iOS.
> When a flag governs *user-visible geometry*, read the platform notes before
> assuming parity.

### F5 — the tab bar discards the bottom safe-area inset

`App.js` passed React Navigation a flat
`tabBarStyle: { height: 70, paddingBottom: 8 }`. Verified against the installed
`@react-navigation/bottom-tabs@6.6.1`, both values defeat its inset handling:

1. `getTabBarHeight()` returns the literal height the moment the flattened style
   carries a numeric one, skipping `49 + insets.bottom` entirely; and
2. `BottomTabBar` spreads `tabBarStyle` **last** in its style array — after its
   own computed `{ height, paddingBottom }` — so the hardcoded padding wins too.

On an iPhone with a home indicator the bar should be **79** tall with **30** of
bottom padding (`49 + max(34 - 4, 0)`). It rendered 70/8. The tab icons and
labels therefore sat in the home-indicator strip, and their touch targets
extended into the system edge-swipe region where iOS eats the first touch.
Android under edge-to-edge had the same bug against the gesture/nav bar, less
visibly.

**Fix:** `src/constants/layout.js` — `tabBarMetrics(insets)`, composed at the
call site. Deliberately **additive** rather than a switch to React Navigation's
own 49-based numbers, so a device reporting `insets.bottom === 0` gets exactly
the 70/8 this app has always shipped. That is the no-regression property, and it
is asserted by literal value in `__tests__/tabBarMetrics.test.js` — not by
re-deriving the formula the implementation uses.

> **The general rule.** Overriding a layout prop on a component that computes
> safe-area insets for you usually *replaces* the computation rather than
> adjusting it. Check the order the library merges your style in; "it looked
> fine on my device" is only evidence about that device's insets.

### F2 — `userInterfaceStyle: "dark"` on a light-themed app

`app.json` declared `"userInterfaceStyle": "dark"`. The design system is light
(`theme.js`: `bg #eef5f1`, white surfaces, deep-green ink) and `App.js` renders
`<StatusBar style="dark" />` — dark *content*, which is only legible on a light
background. The two disagreed, and the app had been shipping the disagreement.

The two platforms do not treat the key the same, which is exactly what hid it.
From Expo's prebuild plugins:

- `withIosUserInterfaceStyle.js` maps `dark` → `UIUserInterfaceStyle = Dark` in
  `Info.plist`, forcing **every system-drawn surface** dark: `Alert.alert`
  dialogs, action sheets, the keyboard, text-selection menus, native pickers,
  scroll indicators.
- `withAndroidUserInterfaceStyle.js` does nothing but emit a warning, and
  `expo-system-ui` is not a dependency — so **Android ignores the key entirely.**

So iPhone users got dark alert boxes over a mint-and-white app, on the purchase,
restore, sign-in, delete-account and scan-error paths — the exact flows a
reviewer walks. Android users never saw it.

**Fix:** one word, `"light"`. Provably a no-op on Android per the plugin source
above, which is why it was safe to change without a device in hand.

> **The general rule.** A shared config key is not necessarily a shared
> behaviour. Before trusting one, read what each platform's plugin actually does
> with it — here one platform wrote a `Info.plist` entry and the other logged a
> warning and moved on.

### F4 — Sign in with Apple used a custom button

`OnboardingScreen.js` drew its own `TouchableOpacity` with an Ionicons
`logo-apple` glyph. `AppleAuthenticationButton` ships in the already-installed
`expo-apple-authentication` and was used nowhere in the app.

Apple's Sign in with Apple HIG — enforced under Guideline 4.8 — expects the
system-provided button. Rendering Apple's trademark from a third-party icon set
is a separate problem again. This is a recurring first-submission rejection note.

**Fix:** render `AppleAuthenticationButton` on iOS, with
`AppleAuthenticationButtonType.CONTINUE` (so the wording matches the copy the
custom button used) and `...ButtonStyle.BLACK` (so it keeps the black fill
against the screen's dark-green gradient). `handleApple` and its busy/error
handling are untouched — only the rendered control changed.

The module is loaded lazily and only on iOS, matching
`authService._loadAppleAuth()`: it has no Android native side, so a static import
would pull an unresolvable native view into the Android bundle. Nothing renders
until the module resolves **and** `isAvailableAsync()` returns true, so a device
that cannot offer Apple sign-in shows no button rather than a dead one, and the
user falls through to Google.

### F6 — iOS permission prompts were English-only

There was no `expo.locales` block, no `CFBundleLocalizations`, no
`InfoPlist.strings` anywhere in the repo.

Android's runtime permission dialogs are drawn by the OS and are already French
on a French device. iOS purpose strings are supplied by the *app*. So a
French-Canadian user — the app's home market — got English camera, photo and
location prompts on iPhone and French ones on Android. That is a straight parity
gap, and a breach of the standing rule in `CLAUDE.md` that no feature ships
without labels in every supported language.

Separately, `NSPhotoLibraryUsageDescription` read "so you can upload receipt and
price-tag images" — but `cameraRollService.js` also **enumerates** the library,
when the user opts in, hunting for unscanned receipts. A purpose string that
understates the actual use is a documented Guideline 5.1.1 rejection ("the
purpose string does not sufficiently explain the use of the photo library").

**Fix:** `assets/locales/{en,fr}.json` wired through `expo.locales`, and the
photo-library string broadened in both languages and in the `app.json` fallback.
`__tests__/iosParityConfig.test.js` derives the required language list from
`translations` in `i18n.js` — the same source `npm run i18n:check` uses — so
adding a third app language automatically requires a third locale file with no
edit to the test.

Three mechanical traps, all pinned by that test.

Because Expo writes each entry verbatim as `KEY = "value";` with **no escaping**:

- a non-plist key (a `_comment`, say) ships as a bogus `Info.plist` entry;
- a straight double quote inside a value produces a malformed `.strings` file.

And because the same file feeds both platforms: keys under `ios` reach
`InfoPlist.strings`, keys under `android` reach `res/values-b+<lang>/strings.xml`,
and **top-level keys go to both**. Written flat — which is how the first draft of
this fix had them — the Android build picks up three unused string resources
literally named `NSCameraUsageDescription` and friends. Harmless (nothing
references them, and `shrinkResources` strips them) but nonsense to find in an
Android binary, and exactly the cross-platform bleed this audit exists to remove.
Nesting under `ios` resolves Android's side to `{}` while still creating the
`values-b+en` / `values-b+fr` folders — which is desirable, since that declares
both locales to Android 13+'s per-app language picker.

> **The general rule.** "The app is localized" is a claim about the JS bundle.
> Everything the *OS* renders on the app's behalf — permission prompts, the
> share sheet, store metadata, notification action titles — is localized
> somewhere else, or not at all. On Android most of it is free; on iOS almost
> none of it is.

## Verified and deliberately NOT changed

Recorded so the next pass doesn't re-investigate:

- `ITSAppUsesNonExemptEncryption: false`, the privacy manifest and
  `NSPrivacyAccessedAPITypes` are present and correct.
- `plugins/withIosPrivacyStringCleanup.js` correctly strips the microphone,
  Face ID, always-location and photo-add strings that dependencies inject. Good
  work — it closes a real 5.1.1 vector and should stay.
- In-app account deletion exists and is reachable (Profile → danger zone →
  `deleteMyAccount`). **Guideline 5.1.1(v) satisfied.**
- No external purchase links anywhere. **Guideline 3.1.1 satisfied.**
- Purchase simulation is gated to `buildProfile === "local"`, so a store build
  cannot grant a tier without a payment sheet — the 3.1.1 trap that a reviewer
  reproduces by tapping Subscribe once.
- `UIBackgroundModes: ["fetch"]` is injected automatically by the
  `expo-background-fetch` / `expo-task-manager` plugins. Nothing owed.
- `PermissionsPrimingScreen` reads `mod?.Camera?.requestCameraPermissionsAsync`
  with no fallback to the top-level export. Checked: expo-camera 55 still ships
  that shim, so it works. **Not a bug** — noted because it looks like one.
- `supportsTablet: false` is fine; iPhone-compat mode on iPad is permitted.
- Location is when-in-use only, requested contextually at the warehouse picker
  rather than up front.

**One open question, not resolved unasked.** The app takes crowdsourced price
submissions. Guideline 1.2 (user-generated content) would require filtering,
reporting, blocking and published contact info — but only if user-submitted
content reaches other users. No such path was found: tag photos go to admin
review only, and the artefact shared onward is the *price*, not the image. That
is the reasoning for treating 1.2 as out of scope. **If a surface exists where
one user sees another user's uploaded photo, this conclusion is wrong** and 1.2
needs a proper pass before submission.

## Regression risk, stated proactively

Every fix was shaped so Android cannot move:

- **F1** — adds a missing import. No behavioural change except that a successful
  restore now succeeds. Both platforms, strictly a repair.
- **F2** — Android provably ignores `userInterfaceStyle` (the plugin only warns,
  and `expo-system-ui` is absent). iOS-only change.
- **F3** — `Platform.OS !== "ios"` evaluates to `true` on Android, i.e. today's
  literal. **iOS behaviour does change**: the crop step disappears there. That is
  the intended fix, but it is a visible change for any existing iOS tester.
- **F4** — the branch is already `Platform.OS === "ios"`-gated; Android never
  entered it. The iOS button's *appearance* changes by design.
- **F5** — additive from the inset. `insets.bottom === 0` reproduces 70/8
  exactly. **Any device with a non-zero bottom inset will see the tab bar get
  taller** — that is the fix, and it is the one change here that alters Android
  layout. On a gesture-nav Android phone the bar grows by ~24dp.
- **F6** — additive files plus a broadened English string, which also becomes
  what English iOS users read (the `.lproj` entry wins over `Info.plist`). This
  incidentally resolves a pre-existing inconsistency: the document-scanner
  plugin was setting a *different* `NSCameraUsageDescription` than `app.json`.
- **eas.json** — a new `device` profile on its own `device` channel. No existing
  profile changed.

**The one to watch on Android is F5.** It is deliberate, but it is the only
change in this branch that moves Android pixels.

Per the standing rule, in the same branch:

  plus the fallback for an unknown tier id and the two failure branches.
- `__tests__/tabBarMetrics.test.js` — the 70/8-at-zero-inset guarantee asserted

## Still owed: on-device verification

None of this has run on an iPhone. Every finding was diagnosed statically, and
two of the fixes (F3, F4) change what the user sees.

The blocker was that no EAS profile could produce an installable iOS binary:
`preview` sets `ios.simulator`, and the rule against dev-client/Metro builds
rules out `development`. This branch adds a `device` profile
(`extends: preview`, own `device` channel, `ios.simulator: false`).

Note the trap it was written around: declaring `"ios": {}` does **not** cancel an
inherited `"simulator": true`, because EAS deep-merges an extended profile. It
has to say `false` explicitly. A profile that looks like it opts out and silently
does not is worse than no profile.

**Checklist — iPhone with a home indicator:**

1. Tab bar — labels clear of the indicator, all five taps register (F5).
2. Any `Alert.alert` — light dialog, not dark (F2).
3. Scan → upload a tall receipt from the library — no square crop, OCR reads the
   whole thing (F3).
4. Sign in with Apple — Apple's own button, completes (F4).
5. Paywall → Restore Purchases with a sandbox sub — success, not "failed" (F1).
6. Device language French, fresh install — camera/photos/notification prompts in
   French (F6).

**Android regression pass, same build:** tab bar spacing (the one that moves),
gallery upload still offers the free-form crop, Google sign-in unchanged.
