# iOS audit #2 — what happens after sign-in

**Date:** 2026-08-10
**Scope:** the iOS surface of the PriceBack mobile app, audited a second time
against the Android build — this time targeting the paths a reviewer never
taps: background execution, locked-device behaviour, token lifetime, and the
labels the OS renders on the app's behalf.
**Branch:** `fix/ios-parity-audit-2`
**Status:** four findings fixed and unit-tested; one documented, not fixed, by
decision. **Nothing has run on an iPhone** — that debt is inherited from the
previous audit and is not discharged here.
**Predecessor:** `Technical/iOS_Audit_2026-08-09.md` (findings F1–F6, PR #249)
**Bugs_Common_Fixes:** #164–#167

---

## Why a second audit

The 2026-08-09 audit was scoped, correctly, to what App Review exercises:
restore purchases, the crop editor, tab-bar insets, dialog chrome, Apple's
sign-in button, permission strings. It found six defects and fixed them.

It stopped at the sign-in screen. Everything past it — how long a token lives,
whether the keychain will hand it back at 3am, what the OS caches on the app's
behalf — went unexamined. That is where this pass went, and it is where the two
worst defects in the app live.

**Both are invisible on Android by construction.** Not "unlikely on Android",
not "less severe" — structurally impossible to observe there. That is why
months of Play traffic never surfaced them, and it is the reason a parity audit
finds things a normal bug hunt does not: the reference implementation is
healthy, so the only symptom is a difference.

Every finding below was confirmed against primary evidence — the installed
`expo-secure-store` Swift sources, the app's own build preflight, the i18n
bundle — not inferred from reading app code.

### A1 — every keychain item was written `WHEN_UNLOCKED`

`expo-secure-store` defaults the accessibility level, and no call site in the
app overrode it:

```swift
// node_modules/expo-secure-store/ios/SecureStoreOptions.swift
var keychainAccessible: SecureStoreAccessible = .whenUnlocked
```

which `SecureStoreModule.swift` maps to `kSecAttrAccessibleWhenUnlocked`. That
attribute means exactly one thing: **the item is readable only while the screen
is unlocked.**

Everything PriceBack runs unattended therefore cannot read the session token on
a phone sitting in a pocket:

- the daily background price check — the app's entire promise;
- both offline scan-queue drains;
- push-token sync.

The failure is silent and actively misleading. `authedFetch` sends the request
with **no** `Authorization` header when the read returns null, so the backend
answers 401 — and the client treats 4xx as terminal. That is precisely the
signature already on file as "the scan worked but no row appeared in the
database", previously attributed to a stale Google token.

**Android cannot reproduce this.** Its SecureStore is Keystore-backed
SharedPreferences with no `setUserAuthenticationRequired`, so lock state is
irrelevant. There is no Android knob that corresponds to the broken one.

Secondary: `WHEN_UNLOCKED` items are carried into encrypted iCloud backups, so
a restored iPhone could inherit another device's session token.

**Fix.** One module, `src/services/secureStore.js`, now owns every keychain
call and writes with `AFTER_FIRST_UNLOCK_THIS_DEVICE_ONLY` — readable after the
user's first unlock following a reboot, and never copied off the device. The
three previous writers (`authService`, `emailSyncService`, `storageService`)
delegate to it and keep their own error policies unchanged.

> **The trap, and it is a good one.** An existing keychain item keeps the
> attribute it was *created* with, so a migration is mandatory — and the obvious
> migration does nothing. `SecItemUpdate` cannot change `kSecAttrAccessible`,
> and expo's `set()` falls back to `update()` on `errSecDuplicateItem` with an
> update dictionary of `[kSecValueData: …]` only. So re-writing the value leaves
> `WHEN_UNLOCKED` in place, and every plausible assertion ("we called
> `setItemAsync` with the option") passes while nothing has changed. The item
> must be **deleted first** so the write takes the `SecItemAdd` path.
> `migrateKeychainAccessibility()` does that, reads before it deletes, and skips
> any key it cannot read — because the failure being fixed *is* an unreadable
> keychain, and treating "invisible" as "absent" would destroy a live token.

> **The general rule.** A cross-platform storage API can expose the same
> function with different *availability* semantics per platform. "Is it
> encrypted?" is the question everyone asks; "when can it be read?" is the one
> that decides whether background work exists.

### A2 — Apple sessions are structurally unauthenticated in the background

**Documented, not fixed** — decision taken during the audit, recorded below.

Apple identity tokens live roughly ten minutes, and `expo-apple-authentication`
exposes **no silent re-issue**: refreshing means presenting the Apple sheet,
which needs a foreground app and a Face ID confirmation. `authService` already
knows this — `_appleReauth` carries a 60-second cooldown whose comment says it
exists so "a background task that can't present UI doesn't retry in a loop".

Google's path has `signInSilently`, wired through `refreshSessionToken`. So:

| | Google (Android + iOS) | Apple (iOS only) |
|---|---|---|
| Token lifetime | ~1 hour | **~10 minutes** |
| Silent refresh | yes | **none — requires UI** |
| Background price check | works | **cannot authenticate** |
| Offline queue drain | works | **cannot authenticate** |
| Push-token sync | works | **cannot authenticate** |

Guideline 4.8 makes Sign in with Apple mandatory once Google is offered, so
this is not a fringe path — it is the default for a large share of iPhone
users, and they get a materially different product from the one on Play.

**Why it was not fixed here.** The correct fix is to stop treating the provider
id-token as the API bearer and mint a first-party session at sign-in — an
access/refresh pair the backend owns and can renew without a human present.
That is an auth-core rewrite touching both platforms, both providers and every
authenticated route. Bundling it with four contained fixes would make the whole
branch unreviewable and put the working Google path at risk to repair the
broken Apple one.

**Design sketch for the follow-up task.** At sign-in, exchange the verified
provider id-token once for a PriceBack refresh token (long-lived, revocable,
stored in the keychain — now with A1's accessibility, which this depends on)
plus a short access token. `authedFetch` uses the access token; refresh is a
plain HTTP call with no UI. Provider tokens are then only ever used at the
moment of sign-in. Two things to get right: revocation must be checked on
refresh so "Sign in with Apple → turn off for PriceBack" still logs the user
out, and the RevenueCat app-user-id must stay bound to the same identifier it
uses today, or entitlements move — see the reasoning already recorded against
identity linking.

**Until then, on iOS, Apple-signed-in users receive price-drop notifications
only via the server-side push path**, not the on-device background check.

### A3 — the badge never came off

`setNotificationHandler` asks for `shouldSetBadge: true`; `sendPriceDropNotification`
carries `badge: 1`. Nothing anywhere in the repo called `setBadgeCountAsync`.

On iOS the icon badge is app-owned state: it stays until the app zeroes it. So
the first price drop put a red dot on the PriceBack icon and it stayed there
forever, through reads, claims and app launches.

Android launchers tie the badge to the notification and clear it on dismiss,
so the platform did the work the app forgot to do — which is why no Play user
ever reported it.

**Fix.** `clearBadge()` in `notificationService`, called when the app comes to
the foreground (`App.js`, deliberately outside the 5-minute hydrate throttle —
it is one native call and the only thing there the user can see on their home
screen) and again after a notification tap is routed. Best-effort and
fire-and-forget: a badge failure must never swallow a tap or block a boot.

### A4 — twelve hardcoded English notification strings

`notificationService` rendered four action-button titles ("View Details",
"Dismiss", "Claim Now", "Remind Tomorrow") and eight titles/bodies for the
price-drop and claim-window alerts as English template literals. None had an
i18n key. A French-Canadian user — the home market — got English notifications
on both platforms.

This is drift, not an unmade decision: the `sendTagScansReadyNotification` and
`sendReceiptScansReadyNotification` senders in the *same file* do it correctly.
A rule that is followed in one function and not its neighbour needs a test, not
a reminder.

Money was formatted as `` `$${n.toFixed(2)}` ``, which bakes the English
currency shape in; Canadian French is `12,34 $`. Only the translated string can
express that, so the amount is now interpolated and each language positions its
own symbol.

**Fix.** All twelve moved to `i18n.js` in both language blocks, rewritten for a
shopper (decision taken: improve the copy rather than transliterate it — so the
English a Play user receives changes too, deliberately). Plus a singular variant
for the one-day case, because `expiryWarnDays` is DB-tunable and could legally
be `1`, which the old string would have rendered as "in 1 days".

> **The iOS-specific half.** Notification categories (iOS) and notification
> channels (Android) both hand the OS a **copy** of their labels, which the OS
> caches and redraws from. Nothing re-reads them when the app language changes,
> so a user who switched to French kept English action buttons and English
> channel names in system settings until they reinstalled. One
> `onLanguageChange` subscription now re-pushes both. Guarded so it installs
> once — stacked listeners would multiply native re-registration calls on every
> switch.

### A5 — the `device` profile warned where it should have failed

`app.config.js`'s store-build preflight refuses to build a store binary whose
RevenueCat key is missing or belongs to the other store. It was fatal only for
`APP_ENV === "production"`.

The `device` profile was added by the *previous* audit as the only profile that
can produce an installable iPhone binary (`preview` is simulator-only, and
dev-client builds are ruled out). It is therefore the build the on-device
checklist runs on — and that checklist's item 5 is "Restore Purchases with a
sandbox subscription", which is also the single control App Review is documented
to exercise for auto-renewable subscriptions.

Because `device` extends `preview`, it inherits `APP_ENV: "preview"` and got a
warning in the build log. The result would have been an hour spent discovering
on a phone that the paywall was inert.

**Fix.** Severity is now keyed off `EAS_BUILD_PROFILE`, not `APP_ENV`, with
`device` joining `production` as fatal. `ALLOW_MISSING_IAP_KEY=1` remains the
explicit opt-out, and every other profile still warns rather than skipping.

> Worth noting for whoever runs that build: locally only the legacy
> `REVENUECAT_API_KEY` exists, and it is a `goog_…` (Play) key, which
> `resolveRevenueCatKeys` correctly refuses to route to iOS. **A
> `REVENUECAT_API_KEY_IOS` (`appl_…`) must exist in the EAS environment** or
> the `device` build will now stop, which is the point.

## Deliberate platform divergences — verified, not defects

Recorded so the next pass does not re-investigate them, and so nobody "fixes"
one by accident.

| Behaviour | iOS | Android | Why |
|---|---|---|---|
| Gallery import *inside* the auto-crop scanner | absent | present | VisionKit has no gallery mode; MLKit has one via the patched plugin. iOS falls back to the system picker, so an uploaded photo gets no edge detection or perspective correction. |
| `maxNumDocuments` | enforced post-hoc by our patch, reports `capturedPageCount` | enforced by MLKit in its own UI | VisionKit has no public mid-session page cap. |
| Camera-roll scan suggestions | supported | refused (`unsupported_platform`) | `READ_MEDIA_IMAGES` is stripped from the manifest for Play compliance, so the permission request would resolve vacuously. |
| Limited photo access ("Select Photos…") | detected and surfaced | n/a | iOS 14+ reports `granted` with `accessPrivileges: "limited"`; handled in `cameraRollService`. |
| Notification channels (importance, vibration, per-channel user control) | n/a | four channels | No iOS equivalent; iOS users get one on/off switch. |
| `stopOnTerminate` / `startOnBoot` | ignored | honoured | Android-only options. On iOS a force-quit stops background refresh until the next manual launch. |
| Modal screens dismissable by swipe | yes | no | `@react-navigation/stack` defaults `gestureEnabled` to true on iOS only. `Scan`, `BarcodeScan` and `PriceTagScan` set it `false`; **`PendingTagScan` and `PendingReceiptScan` do not**, so those two are swipe-dismissable on iPhone and not on Android. Harmless today (nothing is lost on dismiss) but it is an inconsistency, not a decision. |
| App-icon badge ownership | app-owned | launcher-owned | The root of A3. |

Also checked and clean: no `elevation` style without a matching `shadow*` (iOS
shadows render everywhere they should); every `SafeAreaView` comes from
`react-native-safe-area-context`, none from `react-native`; the one
`require("react-native").Platform.OS` in `purchaseService` is a single-property
read, not a namespace import, so it does **not** re-open the crash guarded by
`noReactNativeNamespaceImport.test.js`; `patch-package` runs via `postinstall`,
so the iOS half of the document-scanner patch does reach an EAS build; and the
paywall carries its Guideline 3.1.2 disclosures (auto-renew terms, EULA and
privacy links, language-aware URLs).

**Noticed, not actioned:** `BuyCreditsScreen` — the consumable credit-pack
surface — carries no terms/privacy links of its own. 3.1.2's link requirement
is written for auto-renewable subscriptions, so this is very likely fine, but
it is the one purchase surface with no legal small print anywhere on it.

## Regression risk, stated proactively

- **A1 is the one with real blast radius.** A migration failure leaves that key
  on the old attribute — degraded to today's behaviour, never worse. The
  dangerous window is between the delete and the re-add, where the value exists
  only in memory; if the process dies there, the user is signed out and signs in
  again. Contained by reading first, skipping any key that reads back empty, and
  leaving the migration unflagged so it retries. Worth stating plainly: **iOS
  installs today are TestFlight only**, so the population exposed to this
  migration is approximately one person. There will never be a cheaper time.
- **A1's second deliberate change:** a user restoring an iPhone from an encrypted
  backup now starts **signed out** rather than signed in.
- **A4 changes live Android notification copy.** By choice, and it is the only
  change in this branch a current Play user can see.
- **A3** cannot move Android — `setBadgeCountAsync` is inert there.
- **A5** only narrows which build profiles fail; it starts no new build and
  changes no shipped binary. The one operational consequence: a `device` build
  with no `REVENUECAT_API_KEY_IOS` now stops instead of producing an inert
  binary.
- **A2** is untouched, so it carries no risk — and no improvement.
- Three services now share `secureStore.js`. Each kept its own error policy
  (`authService` warns and returns null, `emailSyncService` lets it bubble,
  `storageService` warns), so no call site's failure behaviour moved.

## Tests shipped with the fixes

- `__tests__/secureStoreAccessibility.test.js` — a source sweep proving no
  module outside `secureStore.js` touches `expo-secure-store` or calls
  `setItemAsync`; that the level chosen is `AFTER_FIRST_UNLOCK_THIS_DEVICE_ONLY`;
  that `keychainWriteOptions` degrades to `{}` rather than
  `{ keychainAccessible: undefined }` and treats `0` as a real level; and — the
  one that matters — that the migration **deletes before it re-adds**, skips a
  key it cannot read, runs once, stays unflagged while a key is deferred, and
  never throws. The managed-key list is checked against the key constants parsed
  out of `authService` and `emailSyncService`, so a rename fails the test
  instead of quietly dropping a key from the migration.
- `__tests__/notificationBadge.test.js` — `clearBadge` zeroes the badge, no-ops
  when the API is absent, swallows a native failure, fires on a notification tap,
  and still routes that tap when clearing throws. Plus source assertions that
  `App.js` calls it on foreground and not behind the hydrate throttle.
- `__tests__/notificationI18n.test.js` — every new key present and non-empty in
  every language (list derived from the bundle, so a third language is covered
  automatically); French genuinely differs from English; placeholders survive
  translation; **no `title`/`body`/`buttonTitle` in the service is a bare
  literal**; no `$${…toFixed}` money formatting remains; the language-change
  re-registration exists and installs one listener.
- `__tests__/easBuildProfiles.test.js` — extended: `device` fails on a missing
  or wrong-store key despite `APP_ENV=preview`, the escape hatch still works,
  `preview` stays a warning, and the message names the profile.

`npm run i18n:check` green (1428 × 2), `npm run typecheck` exit 0. **Suites were
not run locally — CI is the authority (standing rule).**
