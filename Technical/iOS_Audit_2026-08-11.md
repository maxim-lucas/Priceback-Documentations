## Why a fourth audit, and what it could see that the first three could not

| Pass | Date | Ground covered |
|---|---|---|
| #1 (PR #249) | 08-09 | what App Review taps: restore, crop, safe area, dark mode, Apple button, permission prompts |
| #2 (PR #252) | 08-10 | after sign-in: keychain accessibility, background auth, badge, notification i18n |
| #3 (PR #253) | 08-10 | money + identity: sandbox purchases, Google audience, Apple revocation, **first-party sessions** |

Audit #3 shipped a **brand-new authentication subsystem** — session tokens,
`user_sessions`, rotation, reuse detection — in the same branch that audited
everything else. Nothing had ever audited that subsystem, and it is iOS-only by
design. It is also **not yet switched on**: `SESSION_TOKEN_SECRET` is unset on
both Railway services. That is the single most useful fact in this document.
Every session-path defect below can be fixed *before* the feature carries its
first real request, and the two worst ones (A1, A3) become live the moment the
secret is set.

Two themes run through the findings, and neither was reachable by the earlier
passes because both require the previous fixes to exist first:

1. **Lifecycle state is written but never re-read.** Account deletion, Apple
   consent withdrawal and sign-out each write a marker that nothing on the read
   path consults. All three are, in practice, undoable.
2. **Sign-out is not an account boundary.** It clears six keychain keys and
   nothing else. Queued receipt photos, queued tag scans, buffered credit spends
   and the last-known balance all survive into the next account on the same
   handset.

A third observation worth recording as method: **three of the four highest
findings are in code that carries a comment describing the correct behaviour.**
A1's comment explains exactly why the revoke must be `all`, one line after
deleting the credential the revoke needs. S3's comment says a rejected receipt is
"buffered under a synthetic ref … same as the online reject path" while passing
the flag that buffers nothing. C2's rationale ("this just records") is true and
does not mention that the client is therefore the only gate. Reading comments as
statements of intent rather than of fact is what found them.

## A — authentication and account lifecycle

### A1 — withdrawing "Sign in with Apple" revokes nothing server-side

**High · iOS only · in the code audit #3 shipped**

When iOS reports the Apple credential `REVOKED`/`NOT_FOUND`, the client is meant
to kill every first-party session. The comment says so and says why `all` is
required — *"other devices share the same withdrawn consent and this device is
the only one that can see it"* (`src/services/authService.js:621-625`).

It cannot work as written:

```js
620:  await secureDelete(SECURE_KEY_ID_TOKEN);
626:  await revokeFirstPartySession({ all: true }).catch(() => {});
```

`revokeFirstPartySession` builds the `all` request's credential from
`getValidIdToken()` (`:871`), whose first statement is
`if (!idToken) return null` (`:675-676`). No `Authorization` header is sent;
`POST /api/auth/session/revoke` takes the `all:true` branch, `optionalAuthUser`
finds no bearer, and the route answers **401 having revoked nothing**
(`backend/server.js:4398-4402`). The `.catch(() => {})` swallows it.

The local keychain *is* wiped (`:866`), so the handset in the user's hand looks
correct — which is exactly why this would never have been noticed. **Every other
signed-in device keeps a working session for up to 60 days after the user told
Apple to stop.**

**Why it is worth stating as a class, not a bug:** a revocation that depends on
the credential being revoked is circular. The fix reads the token before deleting
it *and* teaches the server's `all` branch to accept a valid refresh token as
proof, so the path no longer depends on a provider credential that is by
definition being withdrawn.

### A2 — "Delete my account" is silently undone, and the 30-day purge never fires

**High · both platforms · PIPEDA 4.5 / Law 25 §28 / GDPR Art. 17 exposure**

`usersRepo.requestDeletion` (`backend/repos/usersRepo.js:530`) is a soft delete:
`status=false`, `deletion_requested_at` stamped, balance zeroed, ledger deleted,
receipts soft-deleted. `jobs/purgeDeletedAccounts` hard-deletes after 30 days.
The design is sound.

What defeats it: **`upsertFromOAuth` unconditionally reactivates the tombstone** —
`status: true, deletionRequestedAt: null` (`usersRepo.js:220-221`) — and it is
called from **eleven** places, only one of which is a deliberate sign-in:

| `backend/server.js` | Route |
|---|---|
| `:4301` | `POST /api/auth/session` (legitimate) |
| `:4707` | **the RevenueCat webhook** |
| `:5003` | `POST /api/me/subscription/sync` |
| `:5104` | `GET /api/me` |
| `:5196` | `GET /api/me/bootstrap` |
| `:5320` | `PUT /api/me/profile` |
| `:5724` | `resolveScanOwner` — **any price-tag scan** |
| `:5777` | `GET /api/me/data-export` |
| `:5953` | `POST /api/me/reset` |
| `:5992`, `:6037` | referral read / redeem |

And `requireAuth` never reads the users row at all, so a soft-deleted account
authenticates normally.

**The path that will actually happen.** Deleting a PriceBack account does not
cancel the App Store / Play subscription (see P1). Thirty days later the
subscription renews, RevenueCat posts `RENEWAL`, `server.js:4707` upserts, the
tombstone flips back to active and `deletion_requested_at` is cleared.
`purgeExpiredDeletions` never sees it again. **The account is never deleted.**

**The faster path.** Any surviving credential. Sessions are revoked on delete
(`server.js:5878`), but the stateless access token stays valid ≤15 min and a
second signed-in device keeps working indefinitely on **Android** — Google's
`signInSilently` re-mints id tokens with no server involvement, so its next
foreground `/api/me/bootstrap` resurrects the account. iOS degrades *more* safely
here: an Apple token dies in 10 minutes and re-auth needs Face ID. Worth
recording because it is the one place in this audit where Android is the weaker
platform.

Reactivation on re-sign-in is intentional and tested
(`backend/tests/duplicateAccountGuardDb.test.js:154`). Reactivation as a side
effect of a webhook or a background sync is not.

### A3 — a stale iOS session token can authenticate the next user of the device

**High · iOS only (sessions are iOS-only) · account confusion**

`authedFetch` (`src/services/authService.js:899-909`) prefers the stored session
access token and **never checks that it belongs to the user currently in the
keychain**:

```js
if (_sessionsSupported()) { token = await _getSessionAccessToken(); ... }
if (!token) token = await getValidIdToken();
```

`isSignedIn()` (`:470`) reads only `auth_id_token`. `signOut()` (`:454-461`)
deletes all six keychain keys in one unordered `Promise.all`, and it does so
*after* an un-timed `fetch` to Google's revocation endpoint (`:444`). A state
where `auth_id_token` is gone but `pb_session_refresh` survives is therefore
reachable — iOS terminating a backgrounded app during that hanging fetch is
enough.

The app then shows the sign-in gate; user B signs in; `_hydrateAfterSignIn()`
(`:229`, fire-and-forget, racing the session mint at `:230`) issues its first
`authedFetch` **as user A**. `syncService.hydrateFromBackend` does not compare the
returned identity to the local one, so A's receipts merge into B's device.

It does not self-heal. `openFirstPartySession()` overwrites the stale session
only if the mint succeeds, and **with `SESSION_TOKEN_SECRET` unset the mint
503s** — so A's refresh token would stay usable for 60 days. The only reason this
is not live today is that no session has ever been minted in production. It
becomes live the moment the secret is set, which is why it is fixed now.

### A4 — account deletion prompts Face ID twice

**High · iOS only · on the exact flow App Review tests for 5.1.1(v)**

`_freshAppleAuthorizationCode()` (`src/services/authService.js:1041`) calls
`AppleAuth.signInAsync()` and keeps only `credential.authorizationCode`,
**discarding the fresh `identityToken` it was handed** (`:1050-1051`). The very
next statement is `authedFetch(DELETE /api/me/account)`, which calls
`getValidIdToken()`; for any user who has been in the app more than ten minutes
the stored Apple token is stale, so `refreshAppleIdTokenInteractive()` presents a
**second** Apple sheet. The two do not share the `_appleReauthInFlight` guard, so
they can also stack.

### A5 — the session routes are the only unauthenticated write path with no rate limit

**Medium · iOS in effect, backend-wide risk**

Every other credit/observation route passes through `creditRateLimited` —
`obs-tag`, `topup`, `receipts`, `referral-redeem`, `device-sync`, `check-drops`,
`offline-scans`, `rc-sync`. The three session routes (`server.js:4288`, `:4345`,
`:4393`) have none, and there is no global limiter: the only `app.use` middleware
are `helmet`, `express.json`, `cors` and the audit logger (`server.js:49-62`).

- `POST /api/auth/session/refresh` is **unauthenticated** and opens a transaction
  that takes a pooled connection and a `pg_advisory_xact_lock`
  (`sessionsRepo.js:68`). Unbounded calls exhaust the Supabase session pooler —
  the most fragile resource in this deployment.
- `POST /api/auth/session` creates an unbounded number of `user_sessions` rows
  per valid provider token. There is no per-user live-session cap.

### A6 — `user_sessions` grows forever

**Medium · both** — `sessionsRepo.pruneExpired`
(`backend/repos/sessionsRepo.js:157`) has **no call site outside tests**.
`sweepScheduler` and the maintenance block (`server.js:7041`, which does wire
`purgeDeletedAccounts`) never invoke it. Revoked rows are retained *by design* so
reuse detection still fires, and rotation inserts one row per refresh — roughly
every 15 minutes of active use, per device. Nothing ever deletes them.

### A7 — `/health` cannot tell an operator whether sessions are switched on

**Medium · both** — audit #3's own S2 lesson was that a bare "configured" hid an
iOS-only failure, and it fixed `/health` to name
`auth.clients.{web,android,ios}` (`server.js:2775-2784`). The subsystem that same
audit shipped got no signal at all: nothing reports `SESSION_TOKEN_SECRET`.
`backend/.env.example:41` documents the var, so the only way to know the feature
is live is to try to mint a session and see whether it 503s.

### A8 — `isSignedIn()` is now wrong on iOS

**Low · iOS only** — it tests `auth_id_token` alone (`:470`). A live 60-day
session with a missing provider token reads as *signed out*, so
`deleteMyAccount`, `resetMyData`, `fetchConsents` and `fetchMyDataExport` all
early-return `auth_required`: the user cannot delete their account or reset their
data while holding a working credential, and the orphaned session survives.

## S — scan pipelines

### S1 — the offline scan queues survive sign-out, and the next account inherits them

**Critical · both platforms**

`signOut()` (`src/services/authService.js:439-462`) deletes six secure-store
keys. It touches no AsyncStorage and no files. `clearAllData()`
(`src/services/storageService.js:1572-1583`) clears
`RECEIPTS_KEY, PREFS_KEY, TAG_SCAN_LOG_KEY, ACCOUNT_CACHE_KEY` plus the credit
cache, and **performs no filesystem work at all** — so it does not clear
`pending_receipt_scans_v1` (`receiptScanQueue.js:37`) or `pending_tag_scans_v1`
(`tagScanQueue.js:29`), nor the persisted images under
`documentDirectory/receipts_pending/` and `documentDirectory/tags/`.

The workers auto-drain with no identity check — `bootService.js:112,114`,
`App.js:389-395` (foreground), `App.js:409-430` (60 s poll),
`notificationService.js:748-756` (background fetch).

**Failure scenario.** A queues a receipt scan offline → signs out → B signs in on
the same handset. On B's next foreground the worker OCRs **A's photo against B's
credit gate** (`receiptScanQueue.js:198-209`), marks it `ready_review` and
notifies B. B sees A's receipt thumbnail and parsed total
(`PendingReceiptScanScreen.js:114-122`), taps "Review & save" (`:143`), and
`POST /api/receipts` persists A's receipt — items, totals, `rawOcr`, warehouse,
and the `memberId` carried in the queued blob (`receiptScanQueue.js:248`,
`receiptParser.js:60`) — under **B's** `sub`. Tags behave identically, with A's
`warehouseId`/`province` captured at scan time (`tagScanQueue.js:101-121`)
submitted from B's account, and B collecting the credit.

Nothing in the code or its comments treats the queues as account-scoped.

### S2 — every iOS scanner capture is written to `Documents/` permanently

**High · iOS only**

`react-native-document-scanner-plugin` writes captures to
`FileManager.default.urls(for: .documentDirectory)` as
`DOCUMENT_SCAN_<page>_<yyyyMMdd_HHmmss>.jpg`
(`node_modules/react-native-document-scanner-plugin/ios/DocScanner/FileUtil.swift:19-27`,
written at `DocScanner.swift:144-147`). `autoCrop.js:117-136`
(`materializeCapturedImage`) **copies** that file into `cacheDirectory/captures/`
and never deletes the source; nothing in the repo ever does (`grep DOCUMENT_SCAN`
outside `node_modules` → zero hits). The plugin exposes `FileUtil.deleteImage`
but no JS surface reaches it.

`deletePersistedImage` (`storageService.js:595-603`) refuses any URI outside
`${documentDirectory}receipts/` — "only delete our own files" — so deleting a
receipt leaves the scanner original, and account deletion leaves it too.

`Documents/` is included in iCloud/iTunes backups by default and nothing sets
`NSURLIsExcludedFromBackupKey`, so a deleted receipt's photo keeps propagating
into backups, with the capture time encoded in the filename to the second. It is
not world-readable (`UIFileSharingEnabled` is not set).

**Android has no equivalent** — MLKit writes into the Play-services cache
(`mlkit_docscan_ui_client`), which the OS reclaims. That asymmetry is precisely
why `materializeCapturedImage` exists (`autoCrop.js:72-76,234-238`).

### S4 — unauthenticated endpoint mints presigned R2 PUT URLs with no size cap

**High · server-side**

`POST /api/observations/tag` (`server.js:2915`) has no `requireAuth` — a
deliberate, documented trade-off for device-attributed anonymous contributions.
Its gates are consent (`:2924`), a client-chosen `deviceId`, and 60/min per
device + 300/min per IP (`:2918-2923`).

Any accepted observation carrying `rawOcr` mints a presigned R2 PUT
(`server.js:3093-3100`), and `getPresignedPutUrl` sends only
`{Bucket, Key, ContentType}` (`backend/storage/r2.js:54-61`) — **no
`ContentLength`, and no `content-length-range` POST policy anywhere in the
repo**; same for GCS (`storage/gcs.js:38-48`). The client uploads the original
capture with no downscale (`priceService.js:655-659`), and the gallery path
allows 20 full-resolution photos at once (`PriceTagScanScreen.js:301-305`) —
unlike receipts, which are resized to 1400 px / 70 % first
(`ScanScreen.js:623-630`). `R2_STORAGE_LIMIT_GB` (`server.js:1496`) is a
`/health` reporting cap, not an enforcement point.

The unauthenticated route is documented. **The missing size cap is not.**

### S5 — queued tags re-submit on partial failure and farm the user's own abuse counter

**Medium · both** — `PendingTagScanScreen.js:43` keeps `results` in component
state only; `:102` passes `initialResults: results[entry.id] || {}` and
`:110-115` removes the queue entry only when `summary.failed === 0`. The only
dedupe is `if (results[i] === "ok") return;` (`priceService.js:837`), which reads
that same state. Meanwhile `tagCreditsRepo.recordAttempt` runs on **every**
submission "(incl. rejected duplicates)" (`server.js:3021-3026`), and
`attempt.overThreshold` sets `status: "flagged_review"`, withholds the credit and
logs `[Fraud]` (`:3033-3041`).

So a 5-tag entry where 4 succeed and 1 fails on a flaky link: the user backs out,
returns, `results` is gone, Submit re-POSTs all five, and the four duplicates
increment the rule-6 rescan counter for the same `(deviceHash, sku, scope)`.
Enough flaky retries and an honest contributor is soft-flagged and earns nothing
— punished for the network.

### S6 — iOS reduced location accuracy seeds the wrong warehouse, and a denied permission is a dead end

**Medium · iOS-primary**

`app.json:33` sets `NSLocationDefaultAccuracyReduced: true` and **nothing calls
`requestTemporaryFullAccuracyAsync` anywhere in the repo**, so there is no route
to precise location on iOS at all. `locationService.js:69-72` tries
`getLastKnownPositionAsync()` then `getCurrentPositionAsync({ accuracy: Low })` —
under reduced accuracy both are the fuzzed (~1–5 km) fix.
`useWarehouseSelection.js:73-82` then seeds `warehouseSel` as nearest-by-fuzzed-
coords **across all provinces**, and that seed is used verbatim for submission
(`PriceTagScanScreen.js:172` → `:163`, and `:549-555`). The only guard is a
one-time confirm dialog (`:606-623`) whose answer is persisted
(`priceTagConfirmedWarehouseId`, `:618`) and never re-asked (`:189-203`).

In Toronto or Montreal several warehouses sit inside the reduced-accuracy radius.
The seed picks the wrong one, the user taps through the confirm once, it is
remembered, and every subsequent observation is attributed to a warehouse they
were never in — corrupting warehouse-scoped medians (`server.js:2981-2998`).

Separately: `locationService.js:61,66` distinguishes denied from services-off,
but `useWarehouseSelection.js:110-129` only offers Open Settings for
`services_disabled`. A plain `"denied"` — terminal on iOS, which never re-prompts
— gets nothing, even though `alertPermissionDenied` exists and is used for camera
and photos (`src/services/permissionAlerts.js`).

The coarse-location *choice* is a deliberate privacy trade-off. The missing
precise-location escape hatch and the missing denied-permission alert are not.

### S7 — legacy `tag/image-uploaded` fallback still allows review-repointing

**Low · server-side** — `server.js:3177-3207` is unauthenticated. The fix at
`:3199-3200` binds the object key to `review.deviceHash`, but `:3201` keeps a
shape-only regex for rows with no stored hash. For any legacy
`tag_scan_reviews` row an anonymous caller can still walk the sequential integer
`reviewId` and repoint another contributor's review at a non-existent key — the
attack the comment at `:3163-3171` describes as closed. Impact is
denial-of-verification: the admin sees a broken photo, the contributor never gets
their credit. Exploitability depends on whether legacy rows exist in prod.

### S8 — the client still transmits the Costco membership number

**Low–Medium · both** — `receiptSyncService.js:64` sends
`memberId: receipt.memberId || null` on every `POST /api/receipts`, and
`ScanScreen.js:1086,1130` persists it in AsyncStorage with the receipt. The
server explicitly discards it: *"DESCOPED (2026-07-24) … We ignore any
`body.memberId` the client sends and never persist it, so the Play Data Safety
form can truthfully answer 'not collected'"* (`server.js:6430-6436`).

So the "not collected" claim rests entirely on one server-side `memberId: null`,
while the number is POSTed to the backend process on every sync and sits in
plaintext AsyncStorage on device. No logging leak is evidenced —
`middleware/audit.js:94-107` logs no bodies and there is no backend Sentry. It is
not in the data export either, which means the stated rule "the membership number
is only allowed in the user's own data export" is currently satisfied by *nobody*
having it. Compliance hygiene: stop sending a field that is by policy not
collected.

### S9 — Veryfi keys are not dev-gated

**Low, latent · both** — `config/profiles/eas.js:62-64` reads
`veryfiClientId/ApiKey/Username` from `process.env` for **every** profile, unlike
`googleVisionApiKey` at `:48`, which is correctly `isDev ? … : undefined`.
`ocrService.js:86-97` reads them from `Constants.expoConfig.extra` (baked into
the bundle), `:111-113` enables the path as soon as they are non-placeholder, and
`:642-660` POSTs the **raw base64 receipt image** from the device straight to
`api.veryfi.com` with the credentials in the header.

Today it is off (`common.js:75-77` placeholders). If anyone ever sets
`VERYFI_API_KEY` in the EAS production environment, a distributable build ships
an extractable partner key and sends unredacted receipt images to a vendor the
privacy manifest does not mention. The line one file over shows the correct
pattern.

## P — platform and App Store compliance

### P1 — account deletion never mentions the App Store subscription

**High · iOS (rejection risk), both (billing harm) · Guideline 5.1.1(v)**

The only prose on the deletion path is `profile.deleteAccountBody`
(`src/services/i18n.js:935`, FR `:2521`): *"We'll erase your profile, credits,
history, watched items, and contributions, and sign you out. Sign back in within
{deletionGraceDays} days to restore your account; after that it's permanently
deleted."* Rendered at `StoresAndProfileScreens.js:1489-1507`.

**No string on this path contains "App Store", "subscription", "abonnement" or
"auto-renew"**, and the modal does not branch on `subStatus?.isPremium` (that
value is only read at `:1095` for the membership-card label). Server-side,
`DELETE /api/me/account` (`server.js:5851-5907`) revokes the Apple credential,
revokes sessions, soft-deletes the user and zeroes credits — and **never contacts
RevenueCat or the App Store**. The subscription keeps auto-renewing.

The only in-app link to `itms-apps://apps.apple.com/account/subscriptions` is at
`ManageSubscriptionScreen.js:387-390`, behind the auth gate the user was just
pushed through (`StoresAndProfileScreens.js:1007` resets to `Splash`).

5.1.1(v) requires an app offering subscriptions to tell the user that deletion
does not cancel the subscription, and how to cancel it. Notable: the codebase
already implements the *other* half of 5.1.1(v) deliberately and cites it by name
(`server.js:5856-5860`, `__tests__/appleAccountDeletionRevoke.test.js`). This is
an omission, not a trade-off.

### P2 — postal code is collected and synced but `PhysicalAddress` is not declared

**Medium · iOS** — postal code is mandatory to finish onboarding
(`OnboardingScreen.js:192`), pushed to the backend (`:279`), persisted (`:292`),
used as the "account exists" marker (`:228`, `SplashScreen.js:157`), and
transmitted per price check (`priceService.js:117`). `app.json:39-115` declares
`CoarseLocation` but no `NSPrivacyCollectedDataTypePhysicalAddress` (repo-wide
grep → 0 hits). The app's own scrubber classifies Canadian postal codes as PII
(`analyticsService.js:30,49`) — an internal admission that this is
identity-grade. Apple files a user-entered postal code under Contact Info →
Physical Address, not Coarse Location.

### P3 — no app-switcher snapshot protection, and no `FLAG_SECURE`

**Medium · both — no divergence, both unprotected** — repo-wide grep for
`FLAG_SECURE`, `preventScreenCapture`, `BlurView`, `secureFlag` → **0 hits**.
Every `AppState` listener acts only on `"active"` (`App.js:347-348`, `:426-427`,
`HomeScreen.js:155-156`, `notificationService.js:72`); nothing handles
`"inactive"`/`"background"` to mask the UI. iOS writes the backgrounded snapshot
to `Library/SplashBoard/Snapshots`, and the captured frame is whatever was on
screen — `DetailScreen` shows a receipt's line items and totals; the scan review
screen shows the receipt photo. Android has the same exposure via the Recents
thumbnail. Mitigating: no membership number is stored in app state, so exposure

## Documented, not fixed

### iOS background execution is materially weaker than Android's

`expo-background-fetch` on iOS uses the iOS-13-**deprecated**
`UIApplication.setMinimumBackgroundFetchInterval`
(`node_modules/expo-background-fetch/ios/BackgroundFetchModule.swift:15`), with
`minimumInterval: 24h` (`notificationService.js:829`). `stopOnTerminate:false`
and `startOnBoot:true` are Android-only, and a force-quit on iOS stops background
fetch until the user relaunches; Low Power Mode suspends it entirely.

**`checkAllPriceDrops` runs only in that task** (`notificationService.js:759`),
so the app's core promise is best-effort on iPhone. The scan queues are mitigated
— foreground `AppState` handler plus a 60 s poll (`App.js:345-430`) — and so is
the credit buffer, which drains from `bootService.js:119` **and** every
`fetchServerCredits()` balance read (`purchaseService.js:752`). Price-drop
detection is the one thing with no foreground equivalent. Worth its own task:
either a foreground sweep on a throttle, or server-side detection pushed down.

### The anti-reinstall device fingerprint is weaker on iOS

`purchaseService.js:282` uses `getIosIdForVendorAsync()` (IDFV), which resets when
the app is deleted; Android uses `getAndroidId()` (SSAID), which does not.
Delete-and-reinstall mints a fresh device identity on iPhone only, so the
signed-out free-scan allowance is re-mintable there. The comment at `:275-276`
acknowledges the IDFV reset; the abuse consequence is not written down anywhere
else.

### With `SESSION_TOKEN_SECRET` unset, iPhones get an Apple sheet during ordinary use

Today's production state. With no session, `authedFetch` falls through to
`getValidIdToken()`, and for an Apple user whose 10-minute token has expired that
calls `refreshAppleIdTokenInteractive()` → `AppleAuth.signInAsync()` → a Face ID
sheet. There is no "am I interactive?" gate; the 60 s cooldown only arms *after*
a failure. It can fire from the foreground `AppState` hydrate before the user has
touched anything. Setting the secret is the fix, and it is an ops step (below),
not a code change.

### Two items need a post-prebuild check, not a code change

`ios/` is gitignored and absent from the working tree, so these cannot be
verified statically:

1. **SDK privacy manifests in `ios/Pods`.** Ours is only the app-level half.
   RevenueCat, Sentry and GoogleSignIn ship theirs in their CocoaPods, and all
   three are on Apple's signed-SDK list — if a pod resolves to a pre-manifest
   version the upload fails with ITMS-91061/91053.
2. **The Sentry iOS dSYM upload phase.** Android's symbolication is pinned in
   `app.json:174,214-216` and covered by a test; there is no equivalent
   assertion for iOS, so an unsymbolicated-crash regression would go unnoticed
   until a crash needs reading.

### P3 — app-switcher snapshot protection: recommended, deliberately not shipped here

The gap is real and both platforms have it. The fix is also small — an overlay
rendered on `AppState` `"inactive"`/`"background"`, plus `FLAG_SECURE` on
Android. It is **not** in this branch on purpose.

iOS reports `"inactive"` for far more than a real backgrounding: a Control
Centre pull, a notification-shade drag, an app-switcher half-swipe, and **every
system permission dialog**. An overlay wired to it flashes over the UI during a
camera or location prompt, which is a visible regression on the app's most
important flow, and the only way to know whether the implementation gets that
right is to watch it on a handset. **Nothing in this project has ever run on an
iPhone.** Shipping a change that repaints on every backgrounding, blind, against
a hard "no regressions" rule, is the wrong trade for a privacy-posture item that
is not an App Review issue and leaks only what is legible in a receipt photo.

It is on the on-device checklist (item 22) and should ship as its own small
change once someone can watch it.

### P6 — "Rate PriceBack" pre-launch: not worth code

`itms-apps://` resolves as soon as the App Store app accepts the scheme, so the
`.catch()` fallback modal never fires and a reviewer lands on an error page. The
condition is **temporary and self-resolving**: it exists only while the listing
is unpublished, and any workaround written now becomes wrong the day it goes
live. Recorded so it is not re-investigated; no code change.

### P4 — why `EmailsOrTextMessages` was removed rather than kept

The declaration is gone from `app.json` and `PhysicalAddress` (P2) is in. Worth
writing down because the obvious objection is "Gmail sync exists in the code, so
keep it": Apple's manifest covers data **collected**, meaning transmitted off
device. Gmail data is a hard local-only constraint here — it never reaches the
backend, OCR or the LLM, and a test guards that — so it is not collected under
Apple's definition even once the feature is switched on. If that constraint ever
changes, the declaration has to come back in the same commit.

### Minor, recorded rather than repaired

- `react-native-document-scanner-plugin` is pinned `^2.0.4` while the patch
  filename hard-codes `2.0.4`; a `2.0.5` publish breaks `postinstall` or silently
  drops the iOS page cap.
- The local analytics path `track()` → `POST /api/analytics`
  (`analyticsService.js:179-192`) applies **no** scrubbing, unlike the Sentry
  path. First-party, but not the same guarantee.
- `ScanScreen.js:5` and `PriceTagScanScreen.js:20` import
  `KeyboardAvoidingView` without rendering it — dead imports from the move to
  `KeyboardAwareScrollView`, carried over from audit #2's "noticed, not
  actioned".
- The price-tag queue still spends its `MAX_OCR_ATTEMPTS = 5` budget on auth
  failures (audit #3's open item). Both root causes are fixed, so the trigger is
  largely gone; separating the error classes in the drain remains its own task.
